# Extracted Skill Rules

Source: `SKILL.md`

## Core Workflow

1. Capture the customer goal before acting. Treat the user's stated goal as a `must` requirement unless they mark it otherwise.
2. Turn the task into a goal contract: goal, must/should/could/wont requirements, acceptance criteria, scope, constraints, risks, verification method, and completion evidence. Each `must` requirement must have explicit evidence before success; success evidence must cite the `req_id` plus an existing current workspace path, a recorded successful validation command, or an existing evidence artifact. Use `rayman goal start`, `run`, `resume`, `status`, and `close` for substantial resumable goals. For long-running work, prefer `rayman goal run --until blocked --checkpoint-interval 10 --max-repair-attempts 3`; it must checkpoint progress, keep advancing through non-human executable inspect/implement/validate/repair/doc-sync paths, stop at summary when completion evidence is still missing, and block only for user-owned input, unavailable external dependencies, or hard validation/release gates that remain after local repair. Blocked/partial waits must record blocker owner, minimum input, evidence path, `rayman goal resume --id <id> --until blocked`, and the automatic resume strategy.
3. Resolve implementation scope before touching files.
4. Establish active skill authority before consuming project-local agent material. Verify workspace skill state, canonical `SKILL.md`, and current installed/current skill hash when available; quarantine retired or shadow surfaces such as old project `.Rayman/` wrappers, stale generated docs, and retired RaymanAgent-like material unless the current workspace contract explicitly reactivates them.
5. Reconcile active contract surfaces before implementation claims: visible requirements, hidden/dot-directory requirements, generated docs, feature coverage, tests, and gate scripts must agree on the behavior being changed. Gate discovery must include hidden contract mirrors when the project uses them, and conflicting old requirements must be retired or updated instead of left active.
6. Map the host execution mode before promising writes. If the host is in Plan Mode or otherwise blocks writes, destructive actions, approvals, or long-running execution, do not claim implementation success; leave a resumable handoff with blocker owner, minimum input, evidence path, resume command, and automatic resume strategy.
7. For non-trivial programming tasks, keep advisory channels separate from host-subagent speed lanes. Advisory channels include `rayman auxiliary advise --task planning -m "goal/context"`, Rayman parallel research roles, and local auxiliary models; they provide evidence-aware suggestions only. Codex host subagents are main-model or other strong-model child agents for speed, not `ai_ubuntu_8888` auxiliary AI. The standalone authorization and closeout rules live in [Host Subagent Auto-Start Authorization](skill-subagent-auto-start-authorization.md); read that file before deciding whether to spawn host subagents. `rayman goal run` and `rayman goal resume` automatically emit `HOST_SUBAGENT_DISPATCH_REQUEST {json}` during non-trivial plan stages when host-subagent lanes are recommended. Use `rayman subagent auto-start --task "<task>" --path <path>` when the primary agent needs host-tool-ready spawn requests, or `rayman subagent plan --task "<task>" --path <path>` to turn a task into recommended host-subagent lanes, an auto-start contract, `spawn_agent` request payloads, record-command templates, dispatch/skip rationale, and main-agent integration duties. Auxiliary AI, research roles, and subagent output are advisory context unless the primary AI assigns a bounded non-overlapping worker edit. If an expected advisory channel or host-subagent lane is unavailable, failed, conflicted, or skipped, the delivery report must include status and reason.
8. Choose the narrowest workflow: `standard_development`, `feature_update`, `documentation_update`, or direct skill calls for simple explain/review/generate/test tasks.
9. Break risky work into atomic operations before editing.
10. After implementing code, run implementation validation. If validation or tests fail and a local repair is possible, enter a repair loop instead of ending the task.
11. Use existing modules under `crates/` and runtime-consumed YAML keys before adding abstractions. Treat YAML keys with no Rust consumer as governance/reference metadata, not runtime switches.
12. Keep gate authority layers separate: project deliverable gates, Rayman broad readiness (`rayman gate status --check`), and goal/session success close prove different claims. Report each layer explicitly and do not promote or demote status across layers without matching evidence.
13. Before adding or changing public docs, skill rules, YAML runtime claims, CLI/API claims, or close-gate claims, update `config/feature_coverage.yaml` with implementation anchors, semantic `test_anchors[].proves`, and validation commands. String-only anchors are not proof.
14. Before deleting, hiding, disabling, or replacing public commands, APIs, config behavior, runtime behavior, generated assets, or skill rules, prove the current surface with context/coverage checks and use asset retirement for obsolete surfaces.
15. Stop or downgrade success when a required operation fails, a `must` requirement lacks evidence, old behavior is not retired, impact was not reviewed, a quality gate fails, local tests fail, review/audit blockers exist, context is stale, or pending work remains.
16. Before final handoff on substantial work, run `rayman auxiliary advise --task workflow_summary -m "summary/verification"` when feasible, then produce a concise execution report with per-requirement evidence and conversation-close auxiliary AI contribution stats.
